# План реализации Gym

Документ разбивает MVP на небольшие вертикальные этапы. Каждый этап должен завершаться работающим и проверяемым состоянием проекта.

## 0. Подготовка проекта

### Задачи

1. Инициализировать Tauri 2 с React, TypeScript и Vite.
2. Настроить единые команды разработки, тестов и сборки.
3. Добавить форматирование и статический анализ:
   - Rust: `rustfmt`, `clippy`;
   - TypeScript: ESLint, Prettier;
   - TypeScript compiler в strict-режиме.
4. Добавить CI для macOS и Linux.
5. Зафиксировать package manager и lock-файл.
6. Добавить базовые ADR:
   - ADR-001: Tauri + React + Rust;
   - ADR-002: SQLite принадлежит Rust-слою;
   - ADR-003: UTC timestamps и локальное активное время.

### Ожидаемая структура

```text
gym/
  .github/workflows/
  docs/
  src/
  src-tauri/
  package.json
  vite.config.ts
  README.md
```

### Готово, когда

- `npm run tauri dev` открывает пустое приложение;
- frontend и Rust-тесты запускаются одной документированной командой;
- CI собирает проект на Fedora 44; macOS собирается локально.

## 2. Планировщик

Статус: **выполнено**.

### Задачи

1. Ввести абстракцию `Clock`:

```rust
trait Clock {
    fn now_utc(&self) -> Timestamp;
}
```

2. Реализовать чистые функции:
   - принадлежность активному периоду;
   - поиск следующего активного времени;
   - расчёт `next_due_at`;
   - reconcile состояния после запуска.
3. Реализовать фоновый scheduler task в Rust.
4. Добавить канал пробуждения scheduler при изменении настроек.
5. Транзакционно создавать pending reminder до показа UI.
6. Реализовать команды:
   - начать сейчас;
   - завершить;
   - отложить;
   - пропустить;
   - поставить на паузу;
   - возобновить.
7. Сделать команды завершения и пропуска идемпотентными.

### Обязательные unit-тесты

- обычное наступление due time;
- переход на следующий активный день;
- выключенный день недели;
- изменение интервала;
- пауза с датой и бессрочная пауза;
- несколько пропущенных интервалов после сна дают один reminder;
- restart при существующем pending reminder;
- повторное завершение одного reminder;
- изменение системной временной зоны;
- граничные значения начала и конца активного периода.

### Готово, когда

Scheduler полностью проверяется с fake clock без ожидания реальных минут и корректно восстанавливается после перезапуска процесса.

### UX-проверки

- длинные русские названия упражнений;
- 1, 3 и 10 упражнений;
- светлая и тёмная тема;

- закрытие окна крестиком не помечает тренировку завершённой.

### Готово, когда

Полный цикл «дождаться → ввести → сохранить → дождаться снова» работает без открытия devtools и сохраняется в базе.

## 7. Сборка и выпуск

Статус: **реализовано**. Подписанный публичный выпуск выполняется по тегу после
настройки Apple secrets и прохождения ручной матрицы из `RELEASE.md`.

### Linux

1. Собирать в контейнере Fedora 44 на GitHub Actions.
2. Выпускать `.rpm` и `.AppImage` для x86_64.
3. Проверить чистую установку, обновление поверх предыдущей версии и удаление без удаления пользовательской базы.

### macOS

1. Собирать arm64 и x86_64 либо universal bundle.
2. Настроить Developer ID signing.
3. Выполнить notarization и stapling.
4. Выпускать `.dmg`.
5. Проверить первый запуск через Gatekeeper и запрос уведомлений.

### Release checklist

- версия обновлена во всех manifest-файлах;
- changelog заполнен;
- миграция с предыдущего релиза протестирована;
- Rust tests, frontend tests, lint и build зелёные;
- ручная тестовая матрица выполнена;
- пакеты установлены на чистые тестовые профили;
- SHA-256 артефактов опубликованы;
- резервная копия тестовой базы успешно восстанавливается.

## Оценка объёма

При работе одного разработчика, знакомого с TypeScript и Rust:

| Этап                              | Ориентир |
| --------------------------------- | -------: |
| Bootstrap и хранилище             |  2–4 дня |
| Планировщик                       |  2–4 дня |
| Окно напоминания                  |  2–3 дня |
| Tray, уведомления, autostart      |  2–4 дня |
| Настройки и история               | 3–5 дней |
| Тестирование, упаковка, полировка | 4–7 дней |

Итого: примерно 3–5 недель на аккуратный MVP. Это ориентир, а не обязательный срок; больше всего неопределённости находится в Linux desktop-интеграции и релизной настройке macOS.

## Первый практический milestone

Первая демонстрационная сборка должна уметь только следующее:

1. Запуститься в tray.
2. Принять интервал в минутах.
3. Через этот интервал открыть окно с тремя упражнениями.
4. Сохранить введённые значения в SQLite.
5. После перезапуска показать сохранённую тренировку и продолжить расписание.

Такой milestone проверяет самые рискованные части архитектуры до разработки полного интерфейса.
